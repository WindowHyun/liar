## 0. 한 줄 요약

기존 주석에 적힌 "규칙 1~7"과 v0.4 정족수 수정은 방향이 맞고 실제로 잘 지켜지고 있습니다.

**(b) 라운드 결과를 확정하는 단일 권위가 없어 각 PC가 "자기가 받은 패킷"만으로 결과를 따로 계산**합니다.
v0.4는 "분모(총 인원)" 불일치를 고쳤지만 "분자(내가 실제로 받은 표)" 불일치는 그대로라, 같은 종류의 장애가 패킷 유실 경로로 재발할 수 있습니다.

## P0 — 즉시 수정 (게임이 눈에 띄게 깨짐)

### P0-1. 브로드캐스트 1건이 항상 2번(멀티 어댑터면 4번) 수신됨 — 중복 제거 없음 **[실측]**

`network.js:80-84`에서 어댑터마다 "계산된 서브넷 브로드캐스트"와 "255.255.255.255"로 **각각** 보냅니다.
두 데이터그램은 같은 링크의 같은 수신 소켓에 **둘 다** 도착합니다. 수신측(`network.js:155`)에는 중복 제거가 없습니다.

실제 재현 결과 (업로드된 `network.js` 그대로 사용, 어댑터 1개):

```
--- DESC 1건 브로드캐스트 ---
수신 #1: {"type":"DESC","id":"PEER1234","nickname":"홍길동","text":"빨갛습니다"} from 192.0.2.2
수신 #2: {"type":"DESC","id":"PEER1234","nickname":"홍길동","text":"빨갛습니다"} from 192.0.2.2
=== 총 수신 건수: 2 (기대: 1) ===
```

영향:
- 채팅(`DESC`) 한 줄이 화면에 **두 번** 찍힘
- `START` 2회 → "게임이 시작되었습니다." 2번 + `votes.clear()` 2번
- `RESULT`/`REVEAL`/`GUESS` 중복 처리
- 이더넷+Wi-Fi 동시 연결(같은 서브넷) PC는 어댑터 2개 × 목적지 2개 = **4배**

주석의 `[규칙 5]`(어댑터별 개별 전송)와 `[이슈1]`(255.255.255.255 추가 전송)은 **송신 측 설계로는 옳습니다**. 문제는 그 대가로 생기는 중복을 **수신 측에서 걷어내지 않은 것**입니다.

수정 방향: 모든 메시지에 `msgId`(예: `${MY_ID}-${seq}`)를 넣고, 수신부에 최근 512개 정도의 LRU/TTL(예: 10초) 중복 필터를 둡니다. 송신 전략은 절대 건드리지 않습니다.

### P0-2. 라운드 결과에 단일 권위가 없음 — 화면마다 결과가 달라질 수 있음 **[코드]**

`game.js:165-201`의 `tryResolveVote()`는 **각 PC가 자기가 수신한 `votes` 맵으로 독립 계산**합니다.
그리고 결정적으로, 결과 경로 중 **브로드캐스트되는 것은 `guess` 경로뿐**입니다.

| 결과 경로 | 전파 방식 | 위험 |
|---|---|---|
| `guess` (`game.js:249`) | `RESULT` 브로드캐스트 | 상대적으로 안전 |
| `wrongAccusation` (`game.js:197`) | `REVEAL` 브로드캐스트 | REVEAL 유실 시 무한 대기 |
| `tie` (`game.js:188`) | **전파 없음, 각자 로컬 계산** | 화면마다 다른 결과 |
| `noVotes` (`game.js:173`) | **전파 없음, 각자 로컬 계산** | 화면마다 다른 결과 |

`VOTE` 패킷 하나가 A에게만 도착하고 B에게 유실되면:
- A: 정족수 충족 → 즉시 집계 → 지목자 X
- B: 30초 타임아웃 → 표 1개 적은 상태로 강제 집계 → 동점(`tie`)이거나 지목자 Y

→ **A는 "X 지목", B는 "동점, 라이어 승"** 이 동시에 뜹니다. v0.4가 고쳤다고 적어둔 증상과 정확히 같은 모양입니다.

또한 지목된 본인만 `REVEAL`을 보내므로(`game.js:196`), 지목자가 갈리면 REVEAL이 2개 나가거나 0개 나갑니다.

수정 방향: 라운드를 시작한 사람을 **라운드 호스트**로 고정하고(이미 `START`에 `id`가 실림), 집계·결과 확정은 호스트만 수행 → `RESULT`를 브로드캐스트, 나머지는 **표시만** 합니다. 호스트가 나가면 라운드 취소를 명시적으로 알립니다.

### P0-3. 라운드 시작 시 역할/제시어를 초기화하지 않음 — 이전 라운드 역할이 남음 **[코드]**

`myIsLiar`/`myWord`(`game.js:30-31`)를 쓰는 곳은 `applyWord()`뿐이고, `START` 수신 처리(`game.js:216-223`)에서 초기화하지 않습니다.

`WORD`는 UDP 유니캐스트 **1회 전송, ACK·재전송 없음**(`game.js:103`)입니다. 이 패킷이 유실되면:
- 2라운드에서 **1라운드의 역할과 제시어를 그대로 들고 게임**을 합니다.
- 1라운드 라이어였다면 2라운드에서도 자신을 라이어로 알고, 지목당하면 `REVEAL isLiar:true`를 보냅니다 → **엉뚱한 사람이 라이어로 판정**됩니다.
- 반대로 시민이면 `myWord`가 옛 제시어라 `GUESS` 판정도 틀립니다(`game.js:247`).

첫 라운드에서 유실되면 `myWord=null, myIsLiar=false` 상태로 "제시어 없는 시민"이 되어, 본인은 아무 안내도 못 받고 화면상 카드도 안 뜹니다(조용한 실패 — 규칙 4 위반).

수정 방향:
1. `START` 처리에서 `myIsLiar=false; myWord=null;` + UI 역할 카드 `pending` 표시
2. `WORD`에 ACK + 재전송(예: 300ms 간격 3회) 도입
3. 일정 시간 내 `WORD` 미수신이면 화면에 "역할을 못 받았습니다 — 호스트에게 재시작 요청" 배너

### P0-4. 같은 PC에서 2개 실행: bind는 성공하는데 유니캐스트가 한쪽만 도착 **[실측]**

`network.js:190-191` 주석은 *"다른 프로세스가 이미 50000번 포트를 쓰고 있어 bind 실패 - 흔히 이 exe를 두 번 실행했을 때 발생"* 이라고 가정하지만, 소켓이 `reuseAddr: true`(`network.js:153`)라 **실제로는 bind가 성공**합니다.

재현 결과:

```
[A] listening OK          <- 두 인스턴스 모두 bind 성공 (EADDRINUSE 아님)
[B] listening OK
[A] GOT HELLO             <- 브로드캐스트는 양쪽 다 수신
[B] GOT HELLO

[B] GOT WORD#0            <- 유니캐스트는 한쪽(마지막 bind)만 수신
[B] GOT WORD#1
[B] GOT WORD#2
```

영향: 한 PC에서 두 명이 참가하면 로비·채팅·투표(브로드캐스트)는 정상 동작해서 **문제없어 보이는데**, 제시어 배분(`WORD` 유니캐스트)만 한쪽에 몰립니다. 한 명은 영원히 역할을 못 받고, 그 원인이 화면·로그 어디에도 안 남습니다.

부수 효과: 잘못된 주석 때문에 `receiveLost` 진단 문구도 실제 원인과 다른 방향을 가리킵니다.

수정 방향: (a) 단일 인스턴스 락(Electron `app.requestSingleInstanceLock()`)으로 2중 실행 차단, 또는 (b) 유니캐스트를 없애고 `WORD`를 "수신자 id + 공유키 암호화" 형태로 브로드캐스트, (c) 최소한 주석과 진단 문구를 실제 동작에 맞게 고칠 것.

### P0-5. UI가 쓰는 `me` 메시지를 만드는 코드가 없음 **[확인필요]**

`public.js:184`는 `case 'me': myId = state.id;`로 자기 id를 받습니다. 그런데 제공된 4개 파일 어디에도 `type: 'me'`를 **보내는 곳이 없습니다**.

```
game.js가 UI로 올리는 타입: accused, awaitGuess, description, networkIssue,
                            participants, result, roundStart, vote, voteStart, word
public.js가 처리하는 타입  : accused, awaitGuess, description, me, networkIssue,
                            participants, result, roundStart, voteStart, word
```

`server.js`에서 `net.MY_ID`를 실어 보내지 않는다면 `myId`는 계속 `null`이고, 그 결과:
- 투표 패널에 **자기 자신이 후보로 표시**됩니다 (`public.js:224`의 `p.id !== myId` 필터가 무력화)
- 지목된 라이어에게 **정답 입력창이 절대 안 뜹니다** (`public.js:245`) → 아무도 GUESS를 못 보내고 **라운드가 영구 정지**

`server.js`를 확인해 `me`를 보내는지 반드시 점검하고, 없으면 추가해야 합니다.

또한 `game.js`가 올리는 `vote` 이벤트를 UI가 **처리하지 않습니다** → 정족수(전원 투표)로 대기하는 구조인데 **누가 아직 투표를 안 했는지 화면에 안 보입니다**. "3/5명 투표함" 표시가 필요합니다.

## P1 — 게임 진행 중 실제로 부딪히는 문제

### P1-6. `startGame()`에 라운드 중복 시작 가드가 없음 **[코드]**
`game.js:78`에는 `roundActive` 검사가 없습니다. 결과 화면에서 시작 버튼이 전원에게 다시 노출되므로(`public.js:251`), 두 명이 거의 동시에 누르면 **START가 2개** 나가고 라이어 2명·제시어 2개로 라운드가 뒤섞입니다. 최소 인원 검사도 없어 **혼자서도 시작**됩니다(본인이 라이어 확정).
→ `if (roundActive) return;`, 최소 3명 검사, 시작 후 잠깐 버튼 잠금.

### P1-7. `GUESS` 판정을 시민 **전원**이 중복 수행 **[코드]**
`game.js:243-252`의 가드는 `if (myWord === null) return;` 뿐이라 **제시어를 아는 모두**가 판정하고 각자 `RESULT`를 브로드캐스트합니다. 5인 게임이면 시민 4명 × 중복 수신 2배 = **RESULT 8건**. 주석의 "실제 제시어를 아는 참가자(나)가 판정"은 실제로 "전원이 판정"입니다.
→ 라운드 호스트만 판정 (P0-2와 동일한 처방).

### P1-8. `CALL_VOTE`를 놓친 피어는 이후 모든 표를 버림 **[코드]**
`registerVote()`(`game.js:154`)는 `if (!votingOpen) return;`으로 시작합니다. `CALL_VOTE` 브로드캐스트를 놓치면 그 PC는 `votingOpen=false`라 **들어오는 VOTE를 전부 폐기**하고, 타임아웃도 안 걸려 있어(`armVoteTimeout`은 CALL_VOTE 수신 시에만 호출) **혼자 이전 화면에 멈춥니다**.
→ `VOTE` 수신 시 투표가 안 열려 있으면 "늦은 투표 시작"으로 간주해 열거나, 호스트가 상태를 주기적으로 재방송.

### P1-9. `REVEAL`/`GUESS` 단계에 타임아웃이 없음 **[코드]**
`awaitGuess`(`game.js:198, 240`) 이후 시간 제한이 없습니다. 라이어가 창을 닫거나 `REVEAL`이 유실되면 **전원이 무한 대기**합니다. 투표(30초)에만 타임아웃이 있습니다.
→ 정답 입력 제한시간(예: 30초) + 미제출 시 시민 승 확정.

### P1-10. `sendBroadcast`의 이중 `close()` → 미처리 예외로 프로세스 종료 가능 **[실측]**
`network.js:93-105`에서 `error` 핸들러와 `send` 콜백이 **각각** `sock.close()`를 호출합니다. 두 경로가 모두 타면 두 번째 호출이 예외를 던집니다:

```
B: 2nd close THREW -> ERR_SOCKET_DGRAM_NOT_RUNNING
```

콜백 안에서 던져지므로 잡히지 않고 Electron 메인 프로세스가 죽을 수 있습니다. 방화벽/보안 에이전트가 아웃바운드를 막는 상황 — 즉 **이 코드가 진단하려던 바로 그 상황** — 에서 터질 확률이 가장 높습니다.
→ `let closed=false;`로 1회만 닫는 `safeClose()` 사용. 더 나아가 **소켓을 매 전송마다 만들지 말고** 어댑터별로 하나씩 재사용(3초마다 어댑터×2개씩 생성/파기 중).

### P1-11. `sendUnicast`의 목적지 IP가 `undefined`면 **자기 자신에게** 전송됨 **[실측]**
`game.js:80`은 `net.getOnlinePeers().find(...)?.ip`로 IP를 구합니다. `currentParticipants()`가 만든 목록과 `.find()`가 다시 부르는 목록 사이에 피어가 타임아웃되면 `ip`가 `undefined`가 되고, Node dgram은 `undefined` 주소를 **`127.0.0.1`로 대체**합니다:

```
C: send cb err = null
C: 127.0.0.1 수신됨! payload= WORD-for-someone-else from 127.0.0.1
```

`WORD` 메시지에는 `id` 필드가 없어 루프백 필터(`game.js:204`)에도 안 걸립니다 → **남에게 갈 역할이 내 역할을 덮어씁니다** (내가 라이어로 바뀌거나, 라이어인데 제시어를 받게 됨).
→ `if (!p.ip) { log(...); continue; }` 가드 + `WORD`에 수신자 `to` 필드를 넣고 `msg.to !== MY_ID`면 무시.

### P1-12. 게임 로직 예외가 "패킷 처리 실패"로 조용히 삼켜짐 **[코드]**
`handleMessage()`는 `network.js:156`의 `try/catch` **안에서** 실행됩니다. 게임 로직의 실제 버그(예: `msg.word.trim()`에서 TypeError)가 JSON 파싱 실패와 구분 없이 로그 한 줄로 끝나고 화면에는 아무것도 안 뜹니다. 규칙 1(수신 루프 생존)은 지켜지지만 규칙 4(조용한 실패 금지)는 반쯤 깨집니다.
→ 파싱 단계와 핸들러 단계의 try/catch를 분리하고, 핸들러 예외는 `diagnosticsHandler`로 UI에도 올릴 것.

## P2 — 견고성·진단·UI

### 게임 로직 (`game.js`)
- **P2-13. 입력 검증 부재**: `sendVote()`(`game.js:144`)는 자기 자신 투표·명단 외 대상·투표 미개시 상태를 막지 않고, `submitGuess()`(`game.js:149`)는 **지목된 라이어가 아니어도 누구나** 정답을 제출해 라운드를 끝낼 수 있습니다. `[수정 6]` 주석이 "UI 잠금은 우회 가능하니 로직에서 막는다"는 원칙을 세웠는데, 투표/정답에는 그 원칙이 적용돼 있지 않습니다.
- **P2-14. 자원 정리 없음**: `setInterval(pushParticipants, ...)`(`game.js:72`)와 `startPresence()`의 인터벌 핸들(`network.js:215`)이 어디에도 저장/해제되지 않습니다. `join()`이 두 번 호출되면 인터벌·수신 소켓이 중복 생성됩니다.
- **P2-15. `knownPeers` 무한 증가**: `network.js:29`의 맵은 타임아웃된 피어를 **삭제하지 않습니다**. 앱을 재시작할 때마다 `MY_ID`가 새로 생기므로(`network.js:28`) 장시간 세션에서 계속 쌓입니다.

### 로깅 (`logger.js`)
- **P2-28. 로그 회전/용량 제한 없음**: 수신 소켓 재생성 루프(`network.js:196`)는 2초마다 로그를 남깁니다. 방화벽에 막힌 상태로 몇 시간이면 파일이 계속 커집니다. 크기 상한(예: 5MB) + 1회 롤오버가 필요합니다.

- **P2-30. `appendFileSync` 동기 I/O**: 패킷마다 로그를 남길 수 있는 경로(`network.js:185`)가 있어, 잘못된 패킷이 쏟아지면 이벤트 루프가 멈춥니다. 비동기 큐 + 배치 flush 권장.
- **P2-31. 로그 레벨 없음**: `[송신 실패]`, `[수신 경고]` 등 접두어로만 구분됩니다. `INFO/WARN/ERROR` 레벨이 있으면 필터링이 쉬워집니다.

## P3 — 설계·유지보수 (지금 당장 깨지진 않음)

- **P3-32. 신뢰 모델 부재**: 같은 LAN의 누구나 `START`/`RESULT`/`REVEAL`/`VOTE`를 위조해 라운드를 끝내거나 결과를 바꿀 수 있습니다. 사내 파티 게임이라면 수용 가능한 위험이지만, **의도된 선택인지 문서에 명시**해 두는 편이 좋습니다. 라운드 시작 시 호스트가 만든 공유 시크릿으로 HMAC을 붙이면 저비용으로 막힙니다.
