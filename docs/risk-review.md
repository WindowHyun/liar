## 한 줄 요약

게임이 실제로 틀어지는 것 **7건**, 특정 상황에서 막히거나 혼란스러운 것 **4건**,
알고만 있으면 되는 것 **6건**을 찾았다.

가장 큰 것은 **호스트 PC에 랜선과 와이파이가 같이 붙어 있으면 2초마다 튕기는 것**(F1)이다.
그다음이 **이미 방을 나간 사람의 표가 개표에 그대로 남는 것**(H1·H2)이다.

## 높음 — 게임이 실제로 틀어진다

### F1. 호스트 PC에 랜선+와이파이가 같이 붙어 있으면 2초마다 튕긴다 **[실측]**

**"최근에 엄청 튕겼다"는 신고를 쫓다 찾았다. 도킹한 노트북에서 아주 흔한 상황이다.**

한 PC가 랜선과 와이파이로 같은 사무실 망에 동시에 붙어 있으면, 그 인스턴스의 알림이
**두 주소에서 번갈아** 도착한다. 예전 코드는 알림이 올 때마다 그 주소로 갈아치웠다.

```
onChange가 불린 횟수 = 10   (2초짜리 알림 5주기 동안)
기록된 호스트 주소 = 127.0.0.1 → 192.0.2.2 → 127.0.0.1 → 192.0.2.2 → ...
```

주소가 바뀌면 `serverUrl`이 바뀌고, 화면은 `onServerChange`에서 **연결을 끊고 다시 붙는다.**
즉 **2초에 한 번씩 튕긴다.** 게임이 사실상 불가능해진다.

**→ 조치**: 쓰던 주소가 아직 살아 있으면(6초 안에 그 주소에서 알림이 왔으면) 다른 주소에서
알림이 와도 갈아타지 않는다. 쓰던 주소가 조용해지면 그때 따라간다(공유기가 IP를 새로 준
경우처럼 진짜로 바뀐 상황). 위 실측이 **10회 → 1회(최초 발견)** 로 줄었다. 테스트 D8


### H1. 이미 나간 사람의 표가 개표에 그대로 남는다 **[실측]**

`vote()`는 **나간 사람에게 투표하는 것**은 막지만(`players.has(targetId)`),
**나간 사람이 이미 던진 표**는 `round.votes`에 그대로 남는다. `tally()`는 그걸 같이 센다.

재현 (4명, 라이어 A):

```
B → C 투표
B 나가기          ← B의 표는 남는다
A → D, C → D, D → C
결과 = liar / tie      (C 2표[B,D] : D 2표[A,C] → 동점 → 라이어 승)
```

B의 표가 없었다면 D가 2표 단독으로 지목되어 결과가 달라진다.
**나간 사람이 판을 가르는 셈**이라, 불리해진 쪽이 표를 던지고 나가면 유리해질 수 있다.

**→ 조치**: 나가면 그 사람이 던진 표를 함께 버린다. 표를 던지고 나가는 것이 이득이 되면
안 되기 때문이다. (`forgetFromRound`, 테스트 W39)

### H2. 이미 방에 없는 사람이 "지목"되어 판이 끝난다 **[실측]**

H1과 같은 뿌리. 나가기 전에 표를 받아 둔 사람이 최다 득표가 되면 그대로 지목된다.

```
C → B, D → B
B 나가기
A → C  (전원 투표 완료 → 개표)
결과 = liar / wrongAccusation
지목된 사람 = B          ← 방에 없는 사람
```

화면에는 `B님이 지목되었습니다`가 뜨고 라이어 승으로 끝난다. 남은 사람 입장에서는
"나가 버린 사람 때문에 졌다"가 된다.

**→ 조치**: 나간 사람에게 갔던 표도 함께 버린다. 그 사람을 찍었던 사람은 다시 고르면 된다.
찬반 단계의 답도 같이 지운다(인원에서는 빠졌는데 답만 남으면 분모·분자가 어긋난다). 테스트 W40·W41

### H3. 게임 서버가 스스로 죽어도 계속 "내가 호스트"라고 알린다 **[실측 + 코드]**

`peer.js`의 `hosting` 플래그는 **호스트를 넘기는 분기에서만** false가 된다.
게임 서버가 다른 이유로 죽으면(포트를 뺏김, 내부 오류) `hosting`은 true인 채로 남고,
UDP 알림에 계속 `isHost: true`를 실어 보낸다.

그러면 다른 PC들은 규칙 1("호스트라고 알리는 쪽이 우선")에 따라 그 PC를 계속 호스트로 보고,
**아무도 서버를 켜지 않는 상태로 굳는다.** 전원이 접속 실패만 반복한다.
`gameServer.isRunning()`이 이미 있으므로, 선출할 때 한 번 확인하면 풀린다.

**→ 조치**: 선출할 때마다 확인해서, 서버가 내려가 있으면 호스트 자리를 내려놓고 다시 정한다.
실제로는 대개 **자기가 다시 켠다**(다른 PC에 넘기는 것보다 낫다). 테스트 D7
— 인스턴스 하나로 확인한다. 여럿이면 다른 PC가 이어받는 경로가 있어 "굳었는지"가 가려진다.

### H4. 제시어 목록이 깨지면 조용히 망가진다 **[실측]**

`web/words.js`를 `[카테고리, 제시어]` 배열로 두는데, 형식 검사가 없다.

| 넣은 값 | 결과 |
|---|---|
| `[]` (빈 목록) | `start()`에서 예외 — 게임이 시작되지 않는다 |
| `['사과']` (배열 아님) | 카테고리 `"사"`, 제시어 `"과"` 로 진행된다 |
| `[[null, '사과']]` | 카테고리 `null` 로 진행된다 |
| `[['과일', '']]` | 제시어가 빈 문자열인 채로 진행된다 |

**제시어 목록을 교체할 예정이라 지금 가장 걸리기 쉬운 항목이다.**
쉼표 하나, 대괄호 하나 빠뜨리면 위 표대로 조용히 이상해진다.
불러올 때 형식을 검사해서 크게 실패시키는 편이 낫다.

**→ 조치**: `validateWordList()`가 불러올 때 검사하고, 몇 번째 항목이 왜 잘못됐는지까지
찍고 실패시킨다. 테스트 W45

### F2. 게임 포트를 다른 프로그램이 쥐고 있으면 조용히 멈춘다 **[실측]**

**예전 버전이 아직 켜져 있는 경우가 대표적이다. 새 버전을 뿌리는 지금 바로 걸린다.**

호스트로 뽑혔는데 TCP 포트를 못 잡으면 세 번 시도하고 포기한다. 그 뒤로는 아무 말도
하지 않아서, 화면은 **"같은 네트워크에서 함께할 참가자를 찾는 중..."에서 영영 멈춘다.**
사용자는 방화벽 문제인지, 아무도 안 켠 건지, 프로그램이 고장난 건지 구분할 방법이 없다.
게다가 선출이 1초마다 도는 자리라 같은 실패가 로그에 계속 쌓였다(20초에 15줄).

**→ 조치**: 포트를 못 잡으면 화면에 "○○번 포트를 다른 프로그램이 쓰고 있습니다.
예전 버전이 켜져 있지 않은지 확인하세요"라고 알린다. 같은 사유는 한 번만 남긴다
(20초에 15줄 → 3줄). 테스트 D9

### F3. 예전 버전(v0.8.0 이하)이 호스트면 20초마다 오류 배너가 뜬다 **[실측]**

v0.8.1부터 화면이 20초마다 연결 확인(`ping`)을 보낸다. v0.8.0 이하 서버는 그 요청을
모르기 때문에 `"잘못된 요청입니다"`로 거절하고, 화면은 그걸 그대로 배너로 띄운다.
**20초마다 오류가 뜨니 고장난 것처럼 보인다.**

| 조합 | 결과 |
|---|---|
| v0.8.1 ↔ v0.8.4 | 문제 없음 (v0.8.1에 이미 `ping`이 있다) |
| v0.8.0 이하가 호스트 | 신버전 화면에 20초마다 오류 배너 |

**→ 조치**: 확인 요청이 거절당하면 그 서버는 예전 버전으로 보고, 배너 대신
"상대가 예전 버전입니다"라고 한 번만 알리고 확인 요청을 그만 보낸다. 테스트 X13

## 중간 — 특정 상황에서 막히거나 혼란스럽다

### M1. 화면 포트가 전부 막히면 창이 안 뜨고 아무 안내도 없다 **[실측]**

`ui-server.js`는 55510부터 10번까지 시도한다. 11개가 모두 사용 중이면 거절하고,
`main.js`의 `uiPort`가 정해지지 않아 **창이 아예 안 뜬다.** 로그 파일에만 남는다.

사용자 입장에서는 exe를 두 번 눌러도 아무 일도 일어나지 않는다.
같은 PC에서 11개를 띄우는 일은 드물지만, 다른 프로그램이 그 대역을 쓰고 있으면 걸린다.
실패했을 때 오류 창이라도 띄워야 한다.

**→ 조치**: 오류 창을 띄우고 로그 위치까지 알려 준 뒤 종료한다.

### M2. 같은 닉네임이 여러 명이면 누구를 찍는지 알 수 없다 **[실측]**

닉네임 중복 검사가 없다. 사무실에서 성이 같은 사람이 겹치기 쉽다.

```
투표 후보 목록 = 철수, 철수, 영희
```

투표 버튼이 `철수` 두 개로 뜬다. 아바타 글자도 같아서 구분이 안 된다.
서버는 id로 정확히 처리하지만, **누르는 사람이 잘못 누른다.**

**→ 조치**: 겹치면 뒤에 번호를 붙인다(`철수`, `철수(2)`, `철수(3)`). 막지는 않는다. 테스트 W42

### M3. WebSocket 한 프레임 크기 제한이 기본값(100MB) **[실측]**

`new WebSocketServer({ server, verifyClient })` 에 `maxPayload`를 주지 않아 기본 100MB다.
참가자 한 명이 큰 프레임을 보내면 서버가 그대로 메모리에 받아 `JSON.parse`를 시도한다.
사내망이라 악의보다는 화면 쪽 버그로 터질 가능성이 크지만, 한 줄로 막을 수 있다.
이 게임이 주고받는 가장 큰 메시지는 300자 채팅이라 16KB면 충분하다.

**→ 조치**: `maxPayload: 16KB`.

### M4. 한 사람이 100줄만 치면 남의 말이 전부 밀려난다 **[실측]**

대화 상한은 방 전체 기준 100줄이다. 사람별이 아니다.

```
B가 "중요한 말" 한 줄 → A가 120줄 도배 → B의 말은 목록에서 사라짐
```

속도 제한(5초에 60개)이 있어 순식간에는 안 되지만, 10초면 충분하다.
게임 흐름상 큰 문제는 아니나, 재접속한 사람이 보는 최근 대화가 통째로 날아간다.

**→ 조치**: 밀어낼 때 **사람이 친 말부터** 버리고 안내(System) 줄은 남긴다. 도배를 해도
"누가 지목됐는지", "결과가 무엇인지"는 남는다. 타자 속도를 제한하지는 않았다. 테스트 W44

## 낮음 — 알고만 있으면 되는 것

### L1. 대화 한 줄마다 10명에게 149KB가 나간다 **[실측]**

상태가 바뀔 때마다 각자에게 **전체 상태**를 다시 보낸다(설계상 의도).
10명 + 대화 100줄 기준으로 1명분이 **14.9KB**, 한 번 뿌리면 **149KB**다.
채팅 한 줄마다 이만큼 나간다. 사내 LAN에서 10명 정도면 문제없지만,
인원이 더 늘거나 Wi-Fi가 나쁘면 체감된다. 늘릴 계획이 있으면 대화만 증분으로 보내는 게 낫다.

### L2. 마지막 투표자만 표를 바꿀 수 없다 **[실측]**

마감 전에는 표를 바꿀 수 있다(`round.votes.set`이 덮어쓴다).
다만 **마지막 사람이 던지는 순간 곧바로 개표**되므로, 마지막 투표자만 번복할 기회가 없다.
**→ 조치 안 함.** 고치려면 마지막 표가 들어온 뒤 몇 초를 더 기다려야 하는데,
매 판이 그만큼 늘어진다. 전원이 던진 순간 바로 개표하는 지금이 더 낫다고 봤다.
번복 기회를 주는 쪽이 좋으면 말해 주면 바꾼다.

### L3. 닉네임 24자 자르기가 이모지를 쪼갤 수 있다 **[실측]**

`slice(0, 24)`는 UTF-16 기준이라 24번째가 이모지 중간이면 깨진 글자가 남는다.
이모지 5개가 길이 10으로 세어지는 것도 같은 이유다.

**→ 조치**: 글자(코드 포인트) 단위로 자른다. 빈 닉네임은 `참가자`로 들어간다. 테스트 W43

### L4. `peer.js`의 `switching` 플래그가 `finally`로 풀리지 않는다 **[코드]**

```js
switching = true;
await gameServer.stop();   // 여기서 예외가 나면
switching = false;         // 이 줄에 도달하지 못한다
```

`stop()`은 내부에서 예외를 잡고 있어 실제로 던질 일은 거의 없지만,
`switching`이 true로 굳으면 **그 PC는 다시는 호스트를 맡지도, 넘기지도 못한다.**
`try/finally`로 두는 편이 안전하다.

**→ 조치**: `try/finally`로 감쌌다.

### L5. 어댑터가 많은 PC는 2초마다 UDP를 여러 갈래로 보낸다 **[코드]**

VPN·VMware·WSL 같은 가상 어댑터가 있으면 어댑터 수 × 2개 목적지로 알림이 나간다.
동작에는 문제가 없지만, 보안 에이전트가 걸고넘어질 수 있다.

### L6. 호스트가 바뀌면 진행 중이던 판은 사라진다 **[설계]**

방 상태는 호스트 PC의 메모리에만 있다. 인계되면 새 호스트에서 빈 방으로 시작한다.
화면에 안내는 나가지만, 이건 구조상 그렇다. (남기려면 상태를 넘기는 층이 필요하다.)

## 문제없다고 확인한 것

아래는 의심해서 들여다봤으나 **문제를 못 찾은** 항목이다.

- **화면에 값을 넣는 경로** — `innerHTML`은 전부 `= ''`(비우기)뿐이고, 사용자 입력은
  모두 `textContent` / `createTextNode`로 붙는다. 닉네임에 `<script>`를 넣어도 글자로만 나온다. **[실측]**
- **제시어 유출** — 무작위 점검 20만 수 동안 라이어에게 전달된 상태에 제시어가 섞인 적이 없다. **[실측]**
- **토큰 유출** — 같은 점검에서 어떤 상태에도 남의 토큰이 실려 나가지 않았다. **[실측]**
- **라이어가 정답을 여러 번 내기** — 첫 제출에서 판이 끝나므로 두 번째는 거절된다. **[실측]**
- **관전자가 투표·제안하기** — `inRound` 검사로 막힌다. **[실측]**
- **정적 파일 경로 탈출** — `path.basename()`으로 잘라내므로 상위 디렉터리로 못 나간다. **[코드]**
- **로그 무한 증가** — 5MB에서 밀어내고 새로 쓴다. **[코드]**
- **타이머 누적** — 무작위 점검에서 200개를 넘긴 적이 없다. **[실측]**

## 고치면서 정한 것

물어보고 진행하려 했으나 "수정해줘"로 답이 와서, 아래처럼 정하고 진행했다.
마음에 안 드는 것이 있으면 되돌리기 쉬운 것들이다.

| 항목 | 정한 것 | 왜 |
|---|---|---|
| H1 · H2 | 나가면 그 사람의 표와 그 사람에게 간 표를 **둘 다 버린다** | 표를 던지고 나가는 것이 이득이 되면 안 된다 |
| M2 | 겹치면 **번호를 붙인다**(`철수(2)`). 막지 않는다 | 사무실에서 이름이 겹친다고 못 들어오게 하면 곤란하다 |
| M4 | **안내 줄을 지키고 사람 말부터 버린다.** 타자 속도는 제한하지 않았다 | 도배를 막겠다고 타자를 막으면 멀쩡한 사람이 더 불편하다 |
| L2 | **그대로 둔다** | 개표를 미루면 매 판이 늘어진다. 이득보다 손해가 크다 |

## 고치면서 같이 나온 것

테스트 도우미 `until()`이 조건 함수의 반환값을 `await` 없이 썼다. 비동기 조건은
Promise를 돌려주는데 Promise는 그 자체로 항상 참이라, **그 조건을 쓴 검사가 통째로
무의미**했다. D7을 만들다 걸렸다(고치기 전 코드로 되돌려도 통과해서 이상해 파 보니 이것이었다).
